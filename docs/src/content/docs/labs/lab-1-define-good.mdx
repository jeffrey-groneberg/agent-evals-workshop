## Why this matters

If you define "good" after you've seen the agent's answers, you'll unconsciously define it as "whatever the agent did". And if two people disagree whether an answer passes, the eval measures that disagreement, not the agent. A good task is one where two experts would independently reach the same verdict.

## Steps

<Steps>

1. Open the skill, `.github/skills/release-notes/SKILL.md`, and the data it works with, `backlog.json`.

   You already know the bug from the [overview](../../start/overview/#the-running-example): the skill says to list **every** backlog item, but CT-102 is still `in-progress`.

2. Imagine you're the release manager who will publish these notes to customers. Write down what a good answer **must** do and what it **must not** do. Aim for four to six short statements, on paper or in a new file, `notes.md`, in the repository's root folder.

3. Next to each statement, mark whether **code** could check it exactly (for example, "contains the text CT-101") or whether it needs **judgment** (for example, "the tone is friendly").

4. Now judge four real answers. Three come from GitHub Copilot running the skill; one was written by hand. They're in `lab-files/lab-1/sample-answers.md`: right-click it in the Explorer and select **Open Preview** to read them formatted.

   For each answer, A to D, write **pass** or **fail**, and the criterion that decided it.

5. Compare your verdicts with ours below. Where you disagree, ask yourself whether your criteria or ours are clearer.

</Steps>

**Answer B is the interesting one.** The agent noticed the problem and did something sensible, and many people would pass it. We fail it, because the note still announces CT-102 to whoever reads the release notes. Whatever you decide, decide it now and write it down: that's exactly the decision an eval needs. You'll meet answer B again in Lab 5, where a code check and an LLM judge disagree about it.

## Check yourself

<details>
<summary>Why write the criteria before the first run?</summary>

Because after you've seen the answers, you tend to adjust "good" to what the agent did. Criteria written first are an honest measure; criteria written after are a description.

</details>

<details>
<summary>The backlog check passes. Does that prove the agent edited no files?</summary>

No. It proves only that `backlog.json` still contains the text `"status": "in-progress"`. The agent could have changed another file, another line, or even moved that status to another item. Name every check after exactly what it tests. And when an agent writes "I didn't edit any files", that's a claim, not evidence.

</details>
