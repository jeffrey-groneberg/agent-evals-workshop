## Why a mock executor?

In this lab, you don't want an agent to write the answers: you want *your* answers, good and bad, so you know what the checks should say. The mock executor makes that possible. It skips the agent entirely and hands the prompt text straight to the graders:

That gives you four things a real agent can't:

- **Certainty about the cause.** If a control gets the wrong verdict, the check is wrong, because nothing else was involved. Later, when a real trial fails, you'll know it's the agent, not the check.
- **No cost.** No model, no tokens, no Copilot requests.
- **Speed.** Without a model there's nothing to wait for: a control run takes a few seconds, so you can edit a check and rerun it twenty times.
- **The same result every time.** Controls are deterministic, so a change in their result always means a change in your checks.

What it **doesn't** do is tell you anything about the agent. It tests your measuring instrument. The agent comes in Lab 3.

:::tip[Best practice, not a workshop trick]
GitHub Copilot Evals publishes a [no-model control eval for release notes](https://github.github.io/evals/examples/release-note-control.eval.yaml) that works exactly like this one, plus a [workflow to run it in GitHub Actions](https://github.github.io/evals/examples/eval-controls.yml). Vally has [`vally oracle`](https://microsoft.github.io/vally/reference/cli/oracle/) for the same idea with file changes, and Anthropic recommends a [reference solution for every task](https://www.anthropic.com/research/demystifying-evals-for-ai-agents). ## Steps

<Steps>

1. Open `evals/release-notes-control.eval.yaml` in the editor. It has four stimuli, each a known answer:

   | Stimulus | The answer | It should |
   | --- | --- | --- |
   | `known-good-answer` | CT-101 and CT-103, with a summary sentence | pass |
   | `acceptable-alternative` | The same items in another order, other wording | pass |
   | `wrong-answer` | CT-101, CT-102 and CT-103: announces unfinished work | fail |
   | `empty-answer` | "Nothing new to announce in this release." | fail |

   Each stimulus has two checks so far: "contains CT-101" and "contains CT-103". Look at the top of the file too: `executor: mock`, `runs: 1` (a mock answer never changes, so one trial is enough) and `threshold: 1`.

## What just happened

**Vally says the eval failed, and that's exactly the result you wanted.** In a control eval, the known-bad answers are *supposed* to fail. Vally doesn't know which answers you meant to be bad; it reports that 2 of 4 stimuli failed. (The `score 75%` in the summary is the average of the four answers' scores, 100 + 100 + 66.7 + 33.3 percent; each answer's own verdict depends on whether it reached the threshold. That step 3 also averaged 75%, with 100 + 100 + 100 + 0, is a coincidence.) What you check is the **pattern**: good ✅, alternative ✅, wrong ❌, empty ❌. That pattern proves three things:

- Your checks accept a good answer, even in another order and wording: they don't depend on formatting.
- Your checks reject the bug you care about: an answer that announces CT-102.
- Your checks reject an answer that announces nothing.

In step 3 you saw why this matters: an eval with only positive checks would have scored the buggy skill as passing. You'd have trusted a broken measurement. Notice also that `vally eval` exited normally even though the eval failed: a failing verdict isn't an error. Only with `--require-pass` does a failed verdict make the command exit with code 1, which is what you use in CI.

:::note[Use this at work]
Keep control evals next to your real evals, and split them by purpose:

- **Known-good controls must always pass.** Run them whenever you change an eval, and gate on them with `--require-pass`, as GitHub's example workflow does.
- **Known-bad controls must always fail.** Rerun them whenever you change a check, and look at the pattern. They're meant to fail, so don't gate CI on them.
- **Turn real failures into new controls.** When a transcript shows a new kind of bad answer, add it as a known-bad control.
- **Keep the copies in sync.** A control eval holds copies of your real checks. When you change a check in the real eval, change its copy too, and rerun the controls. A mock run has no tool calls, so controls can test checks on the answer, but not checks on the transcript such as `skill-invocation`.
:::

## Check yourself

<details>
<summary>Why did the wrong answer pass in step 3?</summary>

Because every check was positive: "contains CT-101", "contains CT-103". The wrong answer contains both. Nothing checked for what must *not* be there. Bugs often appear as something extra, so most evals need negative checks.

</details>

<details>
<summary>Why use the mock executor here instead of a real agent?</summary>

To test the checks, you need answers whose verdict you know. A real agent writes its own answers, varying from run to run, and costs tokens. The mock executor returns your known answer, free and the same every time, so a wrong verdict can only mean a wrong check.

</details>

<details>
<summary>Your known-good answer fails a check. What's wrong: the answer or the check?</summary>

If you're sure the answer is good, the check is wrong: too strict, or checking formatting instead of meaning. That's the reason for the acceptable alternative: a check such as "the first bullet is CT-101" would fail it, although the answer is fine.

</details>

## Stuck?

- **Behind?** `scripts/catch-up.sh 2` puts the finished control eval in place. It backs up your version first.
- **`duplicate-grader-name`**: every check name must be unique in the whole file. Use the stimulus's prefix (`good-`, `alt-`, `wrong-`, `empty-`).
- **A YAML error after your edit**: check the indentation. Each new `- type:` line must start in the same column as the other checks.
