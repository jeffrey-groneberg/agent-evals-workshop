## Why this matters

"I changed the skill and now it passes" isn't proof. The agent varies from run to run; the model behind it can change; you might have changed two things at once. A controlled experiment rules these out: same eval, same model, same settings, same number of trials, one declared difference.

## Steps

<Steps>

1. Fix the skill. Open `.github/skills/release-notes/SKILL.md` and find its first rule:

   ```markdown
   - List every backlog item as a feature of this release, one bullet per item, formatted as `- ID: title`.
   ```

   Replace that whole line with these two lines:

   ```markdown
   - Include only items whose `status` is `done`. Leave every other item out and do not mention it anywhere in the notes.
   - List each included item as one bullet formatted as `- ID: title`.
   ```

   Save the file. The other rules stay as they are.

2. Optional: rerun the eval from Lab 3 to see the effect right away:

   ```bash
   vally eval -e evals/release-notes.eval.yaml
   ```

   In our runs, all three trials passed. But a rerun alone doesn't prove the fix made the difference; the experiment does.

3. Read the experiment file:

   ```yaml title="experiments/skill-fix.experiment.yaml"
   name: release-notes-skill-fix
   evals:
     - ../evals/release-notes.eval.yaml
   # The only setting allowed to differ between variants. Any other difference is an error,
   # so a result can't come from a change you didn't mean to make.
   vary: [/environment/skills]
   baseline: before
   variants:
     before:
       environment:
         skills: ["../skill-versions/before/release-notes"]
     after:
       environment:
         skills: ["../.github/skills/release-notes"]
   ```

   Both variants run the same eval. `before` loads the frozen copy of the original skill, `after` loads your fixed skill. Paths are relative to the experiment file.

4. Check the plan without calling any model:

   ```bash
   vally experiment run experiments/skill-fix.experiment.yaml --dry-run
   ```

   ```text
   Experiment: release-notes-skill-fix
   Baseline:   before
   Plans:      2

   ── before (baseline) ──
     Eval:        release-notes-completed-only
     File:        ../evals/release-notes.eval.yaml
     Model:       claude-sonnet-5.5
     Config hash: 48df94cc2d6ebe75
     Eval hash:   4c5c9c7166d5db5d

   ── after ──
     Eval:        release-notes-completed-only
     File:        ../evals/release-notes.eval.yaml
     Model:       claude-sonnet-5.5
     Config hash: e032d16ce416ef24
     Eval hash:   4c5c9c7166d5db5d
   ```

   The **eval hash** is identical, so both variants run exactly the same eval. The **config hash** differs, because the skills differ. If you haven't changed the eval file or the model, your hashes most likely match ours: they're computed from the settings. What matters is same and different.

5. Run the experiment. It runs three trials per variant, six in all:

   ```bash
   vally experiment run experiments/skill-fix.experiment.yaml
   ```

6. Read the details. An experiment saves its runs in its own folder, `vally-experiment-results/<date-and-time>/`, with one subfolder per variant: `before/` and `after/`, each with the `results.jsonl` and trial folders you know.

   In the Explorer, right-click `report.md` in the newest experiment folder and select **Open Preview**: it has one table per variant. In ours, `before` passed 0 of 3 trials with pass@k and pass^k at 0%, and `after` passed 3 of 3 with both at 100%.

   Read the answers per variant with the shortcut from Lab 3; it picks the newest run, here the experiment:

   ```bash
   ./scripts/answers.sh
   ```

   ```text

   …
   ```

   Do the `after` answers still contain a summary sentence and both done items? A fix that passes the checks but breaks something the checks don't look at is no fix.

7. Compare the variants in the dashboard. It shows one results folder at a time, so point it at the experiment: in the dashboard's terminal, press Ctrl+C, then run:


   Reload the page. The two variants appear as two runs, named after the experiment's run ID with `::before` and `::after`. Scroll down to **Model comparison**, tick both, and select **Compare Selected**:

## What just happened

You proved the fix:

- **Same eval, same model, same settings**: the dry run showed identical eval hashes and the same model.
- **One declared difference**: the skill, the only path in `vary`.
- **A clear result**: 0 of 3 trials passed before, 3 of 3 after. Every check passed after the fix, including the CT-102 check.
- **No hidden cost**: tokens stayed the same, and trials got slightly faster.

The fixed skill's answers look like this one:

```text
This release makes it easier to find things and gives the dashboard a darker look.

- CT-101: Search across all projects
- CT-103: Dark mode for the dashboard
```

## Check yourself

<details>
<summary>Why keep a frozen copy of the old skill instead of using Git history?</summary>

One experiment run needs both versions at the same time, at two different paths. Git history holds the old version, but not as a folder Vally can load next to the new one.

</details>

<details>
<summary>What would Vally do if the after variant also changed the model?</summary>

Refuse to run. The model isn't in `vary`, so a different model would be an undeclared difference. Vally reports it as an error when it plans the experiment, so you can't accidentally credit the skill for a model change.

</details>

<details>
<summary>0 of 3 before, 3 of 3 after. Is the fix proven for good?</summary>

It's strong evidence for this task and this model, from six trials. It's not proof for every request a user might type, and not for future models. That's why you'll keep running the eval on every change, in CI, in Lab 7.

</details>

## Stuck?

- **Behind?** `scripts/catch-up.sh 4` puts the fixed skill in place.
- **A trial shows `ERROR` with `Session disconnected while waiting for a response`**, or another connection problem: the trial didn't finish. It counts neither as a pass nor as a fail, and it skews the comparison of tokens and time, because that variant has fewer finished trials. Run the experiment again. `./scripts/answers.sh` shows such a trial as `ERROR`, with the message.
- **A variant fails with an error that names a path or says `not found`:** a skill path is wrong. Paths in the experiment file are relative to the `experiments/` folder.
- **Your `after` variant still fails:** check your edit against `solutions/lab-4/SKILL.md`, and read the failing answer with `scripts/answers.sh`.

## Go further

`vally compare` goes beyond pass rates: an LLM judge compares the before and after answers pair by pair and estimates which variant is better, with a confidence interval. Add `--compare` to the experiment command to run it right after the trials. It spends tokens on the LLM judge; you choose the judge's model with `--judge-model`. See [vally compare](https://microsoft.github.io/vally/reference/cli/compare/) in the Vally docs.
