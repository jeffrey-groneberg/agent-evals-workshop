**评分器**（grader）判断一次试验是否做到了你想要的结果。它查看回答、运行记录（transcript）或工作区，并返回三样东西：**通过或失败**、一个 0 到 1 之间的**分数**，以及**证据**，也就是它做出判定的理由。评估（eval）的好坏取决于它的评分器：如果评分器分不清好回答和坏回答，所有分数就都失去了意义。

## 三种评分器

| | 代码评分器 | LLM 评审 | 人工审阅 |
| --- | --- | --- | --- |
| **如何判定** | 精确检查某项内容：文本、文件、工具调用 | 由第二个模型应用书面的评分标准（rubric） | 由人阅读并判定 |
| **适合检查** | 事实：“没有宣布 CT-102”、“待办事项列表没有被修改” | 质量：语气、完整性、“开头先有一句总结” | 校准另外两种评分器；不明确的情况 |
| **速度和成本** | 即时，免费 | 需要几秒钟，消耗 token | 慢，耗费人力 |
| **每次结果都一样吗？** | 是 | 不一定 | 不一定 |
| **弱点** | 脆弱：措辞不同的好回答会被判为失败，避开了那段精确文本的坏回答却能蒙混过关 | 可能过于宽松、带有偏差或前后不一致 | 无法规模化 |
| **在 Vally 中** | `output-contains`、`file-contains`、`skill-invocation`、`run-command` 等 | `prompt`（一个评审）、`panel`（多个评审） | 阅读 `eval-results.md` 和运行记录 |

**能用代码评分器的地方就用代码评分器**，代码检查不了的再交给 LLM 评审。再由人来检查这两者，尤其是在刚开始的时候。在练习中，你会先从代码评分器入手，然后在练习 5 中加入评审。

## 检查什么

智能体的工作会留下三类证据，好的评估会在有必要的地方逐一检查：

- **回答**：它是否包含必须包含的内容，并且没有出现不该出现的内容？（`output-contains`）
- **运行记录**：智能体是否做了该做的事，例如使用技能？（`skill-invocation`）
- **工作区**：智能体是否修改了该修改的文件、创建了该创建的文件，并且没有动不该动的文件？（`file-contains`）

大多数情况下，要评的是**产出结果**，而不是过程：智能体可能会用你意想不到的方式得出好的回答，这没有问题。只有当过程本身很重要时才检查过程，例如“使用了技能”或“没有删除任何文件”。

## 肯定检查与否定检查

**肯定检查**在某样东西存在时通过：“回答包含 CT-101”。**否定检查**在某样东西不存在时通过：“回答不包含 CT-102”。在 Vally 中，用 `negate: true` 就能把检查项变成否定检查：

```yaml
- type: output-contains
  name: leaves-out-unfinished-export
  config: { substring: CT-102, negate: true }   # passes when CT-102 is NOT in the answer
```

缺陷往往表现为某样*不该*出现的东西：一个未完成的功能、一条泄露的机密信息、一个被编辑过的文件。只有肯定检查的评估看不到这些问题。你会在[练习 2](../../labs/lab-2-check-your-checks/) 中亲身体验到这一点。

## 检查你的检查项

在信任评分器给出的分数之前，先证明评分器本身是有效的。给它一些你已经知道好坏的答案，看看它的判断是否和你一致：

- **已知正确的答案**必须通过。如果它失败了，说明你的检查项太严格，或者干脆就是错的。
- **可接受的替代答案**（顺序不同、措辞不同）也必须通过。如果它失败了，说明你的检查项依赖的是格式，而不是含义。
- **已知错误的答案**必须失败。如果它通过了，说明你的检查项对你所关心的缺陷视而不见。

这些已知答案称为**对照用例**（control），这个名称来自实验室实验中的对照样本。

### 为什么使用模拟执行器

要把已知答案交给评分器，就不能用真正的智能体：它会写出自己的回答，而不是你准备的答案。Vally 的**模拟执行器**（mock）完全不调用模型，只是把任务的提示词文本原样作为智能体的回答返回。所以你把已知答案写进提示词，评分器评的就正是这段文本。

这样做有四个好处：

- **它把评分器隔离出来**。对照用例失败时，错的一定是评分器，因为没有其他因素参与。以后真实试验失败时，你就知道失败的是智能体，而不是你的检查项。
- **它免费又快速**。不调用模型，不消耗 token，也不产生 Copilot 请求。一次对照运行只需几秒钟，所以你可以随时修改检查项，想重新运行多少次都行。
- **它是确定性的**。相同的对照用例每次都会得到相同的结果。
- **它也能校准 LLM 评审**。把模拟回答交给真实的评审，你就能在让评审给真实回答评分之前，先看看它会如何判定你心中有数的回答。你会在[练习 5](../../labs/lab-5-llm-judge/) 中这样做。

模拟执行器**不能**告诉你任何关于智能体的信息。对照运行只能证明你的测量工具是可靠的，仅此而已。从练习 3 开始，真正的智能体会通过 `copilot-sdk` 执行器运行。

### 最佳实践，而非工作坊里的小技巧

用已知答案检查检查项是一种标准做法：

- **GitHub Copilot Evals** 发布了一个针对发布说明的[无模型对照评估](https://github.github.io/evals/examples/release-note-control.eval.yaml)，以及一个用 `--require-pass` 按需运行该评估的 [GitHub Actions 工作流](https://github.github.io/evals/examples/eval-controls.yml)。
- **Vally** 有一个单独的命令 [`vally oracle`](https://microsoft.github.io/vally/reference/cli/oracle/)，它针对会修改文件的任务，为预先存储的参考解答评分：“如果评分器在正确答案上都不通过，那就是评分器错了。”
- **Anthropic** 建议[为每个任务编写参考解答](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)，这样你就能确认任务是可以通过的，并且评分器配置正确。

在真实项目中，把对照用例和评估放在一起：

- **每次修改评估时，都运行已知正确的对照用例**，并像 GitHub Copilot Evals 示例那样，用 `--require-pass` 把它们作为门禁。它们必须始终通过。
- **修改评分器时，重新运行已知错误的对照用例**。它们*本来就*应该失败，所以要查看它们的结果，而不是把它们作为门禁。
- **把真实的失败变成新的对照用例**。当你在运行记录中发现一个错误的回答时，就把它添加为已知错误的对照用例，让本该发现它的检查项始终名副其实。
- **保持副本同步**。对照用例测试的是你的检查项的副本。在真实评估中修改某个检查项时，也要同步修改它的副本。模拟运行不会产生工具调用，所以对照用例可以测试针对回答的检查项，但不能测试针对运行记录的检查项，例如 `skill-invocation`。

## 修改检查项就是改变测量

如果评估失败后你放宽了它的检查项，通过率会上升，但智能体并没有变得更好。只有当评分器有错时才修改评分器（对照用例会告诉你），当智能体有错时则修改智能体（运行记录会告诉你）。
