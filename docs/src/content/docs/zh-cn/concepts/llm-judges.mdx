有些质量要求无法靠字符串匹配来检查。发布说明是否以一句摘要*开头*？语气是否友好？某条说明是“宣布”了 CT-102，还是只解释了为什么没有包含它？对于这类问题，你可以请第二个模型阅读答案并做出判断。这个模型就是 **LLM 评审**。

## 组成部分

- **评审模型**：负责评分的模型。在练习中，评审模型是 `gpt-5.6-luna`，这是 GitHub Copilot 提供的一个 OpenAI GPT 系列模型；而被测智能体使用的是 Anthropic 的 `claude-sonnet-5.5`。让评审更独立的，正是这种模型系列上的差异；至于评审在哪里运行，只决定它的请求发往何处、由谁付费。在 YAML 中写作 `judge_model`。
- **评分标准（rubric）**：评审所依据的评判标准，每行一条。它就是写给评审的规格说明：凡是评审需要检查的内容，都必须写在里面。
- **评分方式**：评审如何报告它的判定。`binary` 表示通过或失败。Vally 的默认值 `scale_1_5` 表示 1 到 5 分的评分，这个分数会被归一化到 0 到 1 之间，再与该评分器自己的阈值（默认为 0.5）进行比较。这个阈值把评审给出的分数转换为评分器的通过或失败；然后，与其他任何评分器一样，由 `scoring.threshold` 决定整个试验是否通过。
- **证据**：评审可以查看的内容。默认情况下，Vally 会把运行记录（transcript）中的证据交给评审：智能体的输出、它的各项指标以及会话时间线。因此，评审不仅能检查最终答案，还能检查智能体是*如何*完成工作的。
- **评审模型提供方**：评审的请求发往何处。如果不配置，评审就在 GitHub Copilot 上运行，使用与智能体相同的登录身份；练习中就是这样做的。如果添加 `judge_provider` 块，你就可以使用自己的终结点和密钥。

在 Vally 中，评审就是一个 `type: prompt` 的评分器，而评分标准写在任务（stimulus）上：

```yaml
stimuli:
  - name: completed-work-only
    prompt: Write the release notes for this release from backlog.json.
    rubric:                                 # the judge's criteria
      - The answer announces CT-101 and CT-103 as part of this release.
      - The answer does not mention CT-102 anywhere.
      - The answer starts with one short sentence that summarizes the release.
      - The tone is friendly and the answer is short.
    graders:
      - type: prompt                        # the LLM judge
        name: judge-release-notes-quality
        config:
          scoring: binary                   # pass or fail
```

## 编写好的评分标准

- **每行一条标准**，每一条都能单独检查。
- **要具体，不要含糊**。“答案中任何地方都没有提到 CT-102”比“答案是准确的”更好。
- **预先决定边界情况**。如果一条说明解释了为什么没有包含 CT-102，这样可以接受吗？无论你怎么决定，都要把它写下来。如果不写，评审就会替你决定，而且下一次它的决定可能不一样。
- **优先使用二元评分**，尤其是在学习阶段。比起 1 到 5 分的量表，通过或失败更容易拿来和你自己的判断相对照。
- **代码能检查的，就不要交给评审**。“包含 CT-101”是 `output-contains` 的工作：精确、即时，而且免费。

## 评审会在哪些地方出错

关于 LLM 评审的研究（例如 [Zheng et al., 2023](https://arxiv.org/abs/2306.05685)）发现，强大的模型与人类专家意见一致的频率，大致相当于专家彼此之间意见一致的频率；但研究也发现，这些模型存在系统性偏差：

| 问题 | 会发生什么 | 缓解办法 |
| --- | --- | --- |
| **自我偏好** | 模型给自己所属模型系列的输出打分更宽容。 | 选用与智能体属于不同模型系列的评审。 |
| **冗长偏差** | 较长的答案看起来更好，即使实际上并非如此。 | 在评分标准中明确写出对长度或简洁性的要求。 |
| **位置偏差** | 比较两个答案时，排在前面（或后面）的那个更受偏爱。 | 按两种顺序各比较一次，或者单独为每个答案评分。 |
| **宽松与漂移** | 含糊的标准会得到宽松且前后不一致的判定结果。 | 具体的评分标准条目、二元评分，以及校准。 |

## 校准评审

像对待其他任何评分器一样对待评审：**先检查，再信任**。借助[模拟执行器（mock）](../graders/#为什么使用模拟执行器)，把你已经知道判定结果的答案交给它，看看它是否与你的判断一致。如果不一致，要么是你的评分标准不清楚（那就修改评分标准），要么是你自己的预期不清楚（先做出决定，再修改评分标准）。

在[练习 5](../../labs/lab-5-llm-judge/) 中，你将用四个已知答案校准一个评审，并看到代码检查项与评审的判定出现分歧，而且两个方向的分歧都有。下面是我们使用工作坊第一版评分标准时看到的结果：

| 已知答案 | 代码检查项：“不含 CT-102” | LLM 评审 | 谁是对的？ |
| --- | --- | --- | --- |
| 正确：只有 CT-101 和 CT-103，并带有摘要 | <span class="pass">通过</span> | <span class="pass">通过</span> | 两者都对 |
| 错误：宣布了 CT-102 | <span class="fail">失败</span> | <span class="fail">失败</span> | 两者都对 |
| 有一条说明解释了为什么没有包含 CT-102 | <span class="fail">失败</span> | <span class="pass">通过</span> | 取决于你如何定义“好” |
| 条目正确，但没有摘要句 | <span class="pass">通过</span> | <span class="fail">失败</span> | 评审：代码看不出少了一句话 |

两个评分器都不是“更聪明的那一个”。它们体现的是对“好”的不同定义，而评分标准正是你把自己的定义明确写出来的地方。

在实际项目中，还要把评审和人进行比较：时不时请人为一部分真实答案标注判定结果，并跟踪评审与人意见一致的频率。

## 使用你自己的评审模型

默认情况下，评审在 GitHub Copilot 上运行。如果你更希望在自己的模型部署上进行评审，Vally 可以通过 `judge_provider` 把评审的请求发送到你的终结点。它支持三种提供方类型：`azure`（Azure OpenAI 风格的 API）、`openai`（兼容 OpenAI 的 API）和 `anthropic`。本工作坊中可选的自有终结点路径使用 `azure`，例如用于 Azure OpenAI 或 Microsoft Foundry 部署：

```yaml
defaults:
  judge_model: ${JUDGE_MODEL=gpt-5.6-luna}   # with judge_provider: the deployment name on your endpoint
  judge_timeout: 2m
  judge_provider:
    type: azure
    baseUrl: ${JUDGE_BASE_URL=https://set-your-endpoint.invalid/openai/v1/}   # replaced by --param
    wireApi: responses
    apiKeyEnv: LLM_API_KEY
```

运行时使用 `--param JUDGE_BASE_URL="$LLM_BASE_URL" --param JUDGE_MODEL="$LLM_MODEL"` 传入参数。[模型访问与费用](../../start/model-access/#vally-如何使用密钥)逐行解释了这段配置，以及 Vally 实际通过网络发送了什么；[练习 5](../../labs/lab-5-llm-judge/) 介绍了具体步骤。
