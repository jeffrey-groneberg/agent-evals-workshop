## 为什么这很重要

如果你在看过智能体的答案之后才定义“好”，就会不自觉地把它定义成“智能体做了什么就算什么”。而如果两个人对某个答案是否通过意见不一，评估衡量的就是这种分歧，而不是智能体。好的任务，应该让两位专家各自独立地得出相同的判定结果。

## 步骤

<Steps>

1. 打开技能文件 `.github/skills/release-notes/SKILL.md`，以及它要处理的数据 `backlog.json`。

   你已经在[概览](../../start/overview/#贯穿始终的示例)中了解过这个 bug：技能要求列出**每一个**待办事项，但 CT-102 仍处于 `in-progress` 状态。

2. 假设你是发布经理，要把这份发布说明发布给客户。写下好答案**必须**做到什么，以及**绝不能**做什么。目标是写出四到六条简短的陈述，可以写在纸上，也可以写在存储库根文件夹中的新文件 `notes.md` 里。

3. 在每条陈述旁边标注：它能否用**代码**精确检查（例如“包含文本 CT-101”），还是需要**判断**（例如“语气友好”）。

4. 现在来评判四个真实答案。其中三个来自运行该技能的 GitHub Copilot，另一个是人工编写的。它们都在 `lab-files/lab-1/sample-answers.md` 中：在 Explorer（资源管理器）中右键单击它，然后选择 **Open Preview**（打开预览），即可阅读排版后的内容。

   对于 A 到 D 的每个答案，写下**通过**或**失败**，以及起决定作用的那条标准。

5. 把你的判定结果与下面我们的进行比较。如果意见不一致，问问自己：是你的标准更清晰，还是我们的更清晰？

</Steps>

**答案 B 最有意思**。智能体注意到了问题，也做了合理的处理，很多人会判它通过。我们判它不通过，因为它的附注仍然向所有阅读这份发布说明的人宣布了 CT-102。无论你怎么决定，都要现在就做出决定并写下来：这正是评估所需要的决定。你会在练习 5 中再次遇到答案 B，届时代码检查和 LLM 评审会对它得出不同的判定。

## 刚才发生了什么

你为自己的评估写好了规范。在接下来的练习中，每条标准都会变成一个检查项：

| 标准 | 变成 | 练习 |
| --- | --- | --- |
| 1、2 | `output-contains` 检查项（肯定检查） | 2 |
| 3 | 带有 `negate: true` 的 `output-contains` 检查项（否定检查） | 2 |
| 4 | 针对运行记录的 `skill-invocation` 检查项 | 3 |
| 5 | 针对工作区的 `file-contains` 检查项 | 3 |
| 6、7 | 供 LLM 评审使用的评分标准条目 | 5 |

## 自我检查

<details>
<summary>为什么要在第一次运行之前写下标准？</summary>

因为看过答案之后，你往往会按照智能体的实际做法去调整“好”的定义。事先写下的标准是一把诚实的尺子；事后写下的标准只是一段描述。

</details>

<details>
<summary>待办事项检查通过了。这能证明智能体没有编辑任何文件吗？</summary>

不能。它只能证明 `backlog.json` 仍然包含文本 `"status": "in-progress"`。智能体可能修改了另一个文件、另一行，甚至把这个状态挪到了另一个条目上。给每个检查项命名时，要准确说明它检查的是什么。而当智能体写下“I didn't edit any files”时，那只是一种说法，而不是证据。

</details>
