## 为什么使用模拟执行器？

在本练习中，你不希望由智能体来写答案：你要的是**你自己的**答案，有好有坏，这样你才清楚检查项应该得出什么结论。模拟执行器正好能做到这一点。它完全跳过智能体，把提示词文本直接交给评分器：

这带来了四点真实智能体给不了的好处：

- **原因明确**。如果某个对照用例得到了错误的判定结果，那就是检查项错了，因为没有其他因素参与。以后真实试验失败时，你就知道问题出在智能体，而不是检查项。
- **零成本**。不用模型，不耗 token，也不消耗 Copilot 请求。
- **速度快**。没有模型，也就无需等待：一次对照运行只需几秒，你可以改一个检查项，然后重跑 20 次。
- **每次结果都相同**。对照用例的结果是确定的，所以结果一旦变化，必然意味着你的检查项变了。

但它**不会**告诉你任何关于智能体的信息。它测试的是你的测量仪器。智能体要到练习 3 才登场。

GitHub Copilot Evals 发布了一个[无模型的发布说明对照评估（eval）](https://github.github.io/evals/examples/release-note-control.eval.yaml)，工作方式与本练习中的这个完全相同，还提供了一个[在 GitHub Actions 中运行它的工作流](https://github.github.io/evals/examples/eval-controls.yml)。Vally 提供 [`vally oracle`](https://microsoft.github.io/vally/reference/cli/oracle/)，把同样的思路用在文件改动上；Anthropic 也建议[为每个任务准备一个参考解法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。参见[评分器：检查你的检查项](../../concepts/graders/#检查你的检查项)。

## 步骤

<Steps>

1. 在编辑器中打开 `evals/release-notes-control.eval.yaml`。它包含四个任务，每个都是一个已知答案：

   | --- | --- | --- |
   | `known-good-answer` | CT-101 和 CT-103，外加一句摘要 | 通过 |
   | `acceptable-alternative` | 相同的条目，但换了顺序和措辞 | 通过 |

## 刚才发生了什么

**Vally 说评估失败了，而这正是你想要的结果**。在对照评估中，已知错误的答案**本来就应该**失败。Vally 并不知道哪些答案是你有意写坏的；它只报告 4 个任务中有 2 个失败。（汇总中的 `score 75%` 是四个答案分数的平均值，这四个分数分别是 100%、100%、66.7% 和 33.3%；而每个答案自身的判定结果，取决于它是否达到了阈值。第 3 步的四个分数是 100%、100%、100% 和 0%，平均值同样是 75%，这纯属巧合。）你要检查的是**模式**：好答案 ✅、替代答案 ✅、错误答案 ❌、空答案 ❌。这个模式证明了三件事：

- 你的检查项会接受好答案，即使换了顺序和措辞也一样：它们不依赖格式。
- 你的检查项会拒绝你关心的那个 bug：一个宣布了 CT-102 的答案。
- 你的检查项会拒绝什么都没宣布的答案。

第 3 步已经让你看到了这为什么重要：只有肯定检查的评估，会把有 bug 的技能（skill）判为通过。那样你就会信任一个本身就有问题的测量。还要注意，尽管评估失败了，`vally eval` 仍然正常退出：失败的判定结果并不是错误。只有加上 `--require-pass` 时，失败的判定结果才会让命令以退出码 1 退出，这正是你在 CI 中要用的。

:::note[在实际工作中运用]
把对照评估和真实评估放在一起，并按用途拆分：

- **已知正确的对照用例必须始终通过**。每次修改评估时都运行它们，并像 GitHub 的示例工作流那样，用 `--require-pass` 把它们设为门禁。
- **已知错误的对照用例必须始终失败**。每次修改检查项时都重新运行它们，并查看结果的模式。它们本来就应该失败，所以不要把它们设为 CI 的门禁。
- **把真实的失败变成新的对照用例**。当运行记录（transcript）中出现一种新的错误答案时，把它添加为已知错误的对照用例。
- **保持副本同步**。对照评估保存的是你真实检查项的副本。在真实评估中修改某个检查项时，也要修改它的副本，并重新运行对照用例。模拟运行没有工具调用，所以对照用例能测试针对答案的检查项，却无法测试针对运行记录的检查项，例如 `skill-invocation`。
:::

## 自我检查

<details>
<summary>为什么错误答案在第 3 步中通过了？</summary>

因为所有检查项都是肯定检查：“包含 CT-101”“包含 CT-103”。错误答案两者都包含。没有任何检查项去检查**不应该**出现的内容。Bug 往往表现为多出来的东西，所以大多数评估都需要否定检查。

</details>

<details>
<summary>为什么这里用模拟执行器，而不用真实的智能体？</summary>

要测试检查项，你需要判定结果已知的答案。真实智能体会自己写答案，每次运行都不一样，还要消耗 token。模拟执行器返回的是你的已知答案，免费且每次都相同，所以判定结果一旦出错，只可能是检查项错了。

</details>

<details>
<summary>你的已知正确答案没通过某个检查项。错在哪里：答案还是检查项？</summary>

如果你确定答案是好的，那就是检查项错了：要么太严格，要么检查的是格式而不是含义。这正是设置可接受替代答案的原因：像“第一个列表项是 CT-101”这样的检查项会让它失败，尽管这个答案完全没问题。

</details>

## 遇到问题了？

- **进度落后了？**`scripts/catch-up.sh 2` 会把完成版的对照评估放到位。它会先备份你的版本。
- **`duplicate-grader-name`**：每个检查项的名称在整个文件中都必须唯一。请使用该任务的前缀（`good-`、`alt-`、`wrong-`、`empty-`）。
- **编辑后出现 YAML 错误**：检查缩进。每个新加的 `- type:` 行都必须与其他检查项从同一列开始。
