## 为什么这很重要

评审也是评分器，而评分器是会出错的。评审出错的方式比字符串检查更难预测：它可能过于宽松，可能按自己对“好”的理解来判断，也可能对不明确的情况每次给出不同的判定。所以，你要像对待练习 2 中的检查项那样对待它：先通过**模拟执行器**使用已知答案，这样被测试的只有评审，消耗 token 的也只有评审。

## 开始之前

这里不需要做任何设置：评审在 GitHub Copilot 上运行，使用与智能体相同的登录身份。评估文件使用 `gpt-5.6-luna` 作为评审模型。如果你的 Copilot 计划中没有这个模型，请参阅[卡住了？](#卡住了)。如果你更想在自己的模型终结点（例如 Azure OpenAI 部署）上运行评审，请先按本文完成练习，然后按照末尾的[使用你自己的终结点](#使用你自己的终结点)操作。

<Steps>

1. 把评审的对照用例复制到 `evals/`：


   打开 `evals/judge-controls.eval.yaml`，找到以下几个部分：

   - `executor: mock`：这四个答案又是已知答案，分别是练习 1 中答案 C、A、B 和 D 的缩短版。答案 B 保留了关于 CT-102 的备注，但去掉了“可以把 CT-102 加回来”的提议。

   - `rubric: &rubric`：四条标准，只定义一次，再通过 `*rubric` 在每个答案中复用。请仔细阅读第二行：“Saying that CT-102 is unfinished or was left out is acceptable.”（指出 CT-102 尚未完成或被略去是可以接受的。）

   ```bash
   vally lint -e evals/judge-controls.eval.yaml --strict
   ```

3. **预测**每个判定结果：代码检查项会怎么判，评审又会怎么判。然后运行：

   ```bash
   vally eval -e evals/judge-controls.eval.yaml
   ```

   评审处理每个答案需要几秒钟。我们的一次运行结果：

   | --- | --- | --- | --- |

   | `note-mentions-unfinished-item` | <span class="fail">失败</span> | <span class="pass">通过</span> | “The response satisfies every release-note requirement: it announces CT-101 and CT-103, excludes CT-102 appropriately, starts with a concise summary…” |
   | `no-summary-sentence` | <span class="pass">通过</span> | <span class="fail">失败</span> | “…the answer fails the required opening-summary-sentence criterion.” |

4. 看看这两处分歧。它们的方向正好相反：

   - **没有概括句的答案**：代码检查项判它通过，因为其中没有 CT-102。评审判它失败：它看到了任何字符串检查都看不到的问题，即缺少开头的概括句。在这里，评审做到了只有评审才能做到的事。
   - **关于 CT-102 的备注**：代码检查项判它失败，评审判它通过。**按各自的定义**，两者都是对的。评分标准明确允许加一条备注，代码检查项则完全不允许提及。而你在练习 1 中认定，这样的备注是不可接受的。

   评审完全是按评分标准行事的。与你对“好”的定义不一致的，其实是评分标准。

5. 让评分标准与你的定义一致。在 `evals/judge-controls.eval.yaml` 中，找到评分标准的第二行：

   ```yaml
         - The answer does not announce CT-102 (Export reports to CSV) as part of this release. Saying that CT-102 is unfinished or was left out is acceptable.
   ```

   把这一整行替换为下面这行，并保留 `-` 前面的 6 个空格：

   ```yaml
         - The answer does not mention CT-102 (Export reports to CSV) anywhere, not even to say that it was left out or comes later.
   ```

   再次运行第 3 步中的同一条命令，并用同一条 `jq` 命令查看评审的判定结果。现在，评审也判定带备注的答案失败了：

   | 答案 | 代码检查项 | 评审 |
   | --- | --- | --- |
   | `known-good-answer` | <span class="pass">通过</span> | <span class="pass">通过</span> |
   | `wrong-answer` | <span class="fail">失败</span> | <span class="fail">失败</span> |
   | `note-mentions-unfinished-item` | <span class="fail">失败</span> | <span class="fail">失败</span> |
   | `no-summary-sentence` | <span class="pass">通过</span> | <span class="fail">失败</span> |

   现在，评审和代码检查项在事实层面达成了一致，而评审还补上了代码看不到的那一点。

6. 把校准好的评审加入真实的评估。请把它作为一个新文件添加，这样练习 3 中的评估就能保持不变，继续用于实验和 CI：

   ```bash
   cp solutions/lab-5/release-notes-judged.eval.yaml evals/
   ```

   打开 `evals/release-notes-judged.eval.yaml`，与 `evals/release-notes.eval.yaml` 进行比较。它们是同一个评估，只多了三处内容：`defaults` 下的 `judge_model`、任务（stimulus）上严格版的 `rubric`，以及第六个评分器：

   ```yaml
         - type: prompt
           name: judge-release-notes-quality
           config:
             scoring: binary
   ```

7. 运行它：使用修复后的技能，对真实的智能体进行 3 次试验，每次试验都由 5 个代码检查项和评审来评分：

   ```bash

   ```


</Steps>

## 刚才发生了什么

- 你在信任评审之前先**校准**了它，用的是和练习 2 相同的技巧：通过模拟执行器提供已知答案。只有评审在运行，也只有评审消耗了 token。
- 你看到评审和代码检查项可能**在两个方向上产生分歧**，而每一次分歧都能让你学到东西：一次是关于代码看不到的内容，一次是关于评分标准没有写明的内容。
- 你**修改的是评分标准，而不是评审**。评分标准就是评审的规格说明。
- 你在试验记录中**读到了评审的理由**，每个检查项的证据都保存在那里。
- 你以单独文件的形式**把评审加入了真实的评估**：快速、免费、确定性的代码检查项留在 `release-notes.eval.yaml` 中，用于实验和 CI；带评审的评估则补充了那些需要判断的质量要求。

评审会让每次试验多一次模型调用，而且速度更慢：在我们的运行中，每次试验耗时从几秒到约 2 分钟不等，取决于服务的负载。这也是在代码检查项够用的地方就使用代码检查项的又一个理由。

## 自我检查

<details>
<summary>为什么要用模拟执行器校准评审？</summary>

因为你需要一些已知判定结果的答案，才能看出评审是否与你一致。模拟执行器不经过智能体，原样提供你的答案：智能体这一侧不产生费用，每次结果都一样，出现任何意外都只能是评审造成的。

</details>

<details>
<summary>在第 3 步中，评审判定关于 CT-102 的备注通过，代码检查项却判它失败。谁是对的？</summary>

按各自的定义，两者都对：评分标准允许加备注，代码检查项则完全不允许提及。真正的问题是，哪个定义才是你的。你在练习 1 中决定不接受这样的备注，所以你修改了评分标准，把这一点写明。

</details>

<details>
<summary>智能体用的是 Claude 模型，为什么评审用的是 GPT 模型？</summary>

模型在评判与自己同类的输出时，往往会过于宽容；研究人员把这称为自我偏好偏差。来自另一个模型系列的评审更加独立。如果你把智能体换成 GPT 模型，也请通过 `--param JUDGE_MODEL=<model-id>` 选择另一个系列的评审模型。

</details>

```yaml title="solutions/lab-5/judge-controls.eval.yaml" ins={36}
# Lab 5 solution (step 5): the judge controls with the stricter rubric.
#
# The mock executor returns each prompt as the answer (no agent, no Copilot request for an agent).
# Each answer is graded twice: by the code check from Lab 2 (is CT-102 absent?) and by an LLM
# judge that reads the answer and the rubric. Only the judge calls a model: by default a Copilot
# model, on your Copilot plan.
#
# Run it:
#   vally eval -e evals/judge-controls.eval.yaml
# Another judge model: add --param JUDGE_MODEL=<model-id>. Your own endpoint: see Lab 5 on the site.
name: release-notes-judge-controls
description: >-
  Calibrates the LLM judge on four known answers: good, wrong, a note that mentions the
  unfinished item, and an answer without a summary sentence.
defaults:
  executor: mock
  runs: 1
  timeout: 60s
  judge_model: ${JUDGE_MODEL=gpt-5.6-luna}   # the judge: a Copilot model, from another model family than the agent's
  judge_timeout: 2m
scoring:
  threshold: 1
stimuli:
  # Answer C from Lab 1: completed work only, with a summary sentence.
  - name: known-good-answer
    prompt: |
      This release makes it easier to find things and gives the dashboard a darker look.

      - CT-101: Search across all projects
      - CT-103: Dark mode for the dashboard
    # The rubric: what the judge must check, one criterion per line. Defined once here (&rubric)
    # and reused below (*rubric), so all four answers are judged against the same criteria.
```

## 卡住了？

- **进度落后了？** `scripts/catch-up.sh 5` 会把两个完成版文件都放到位，其中包含严格版的评分标准。
- **你的计划中没有评审所用的模型**：启动 `copilot`，输入 `/model`，选择另一个模型（最好与智能体的模型属于不同系列），然后加上 `--param JUDGE_MODEL=<model-id>` 运行。要永久修改默认值，请编辑两个评估文件中的 `judge_model` 行。
- **评审的每次评分都无效**：评审无法给出回答时，Vally 会把这次评分标记为无效，而不是判为通过。用 `./scripts/check-setup.sh` 检查你的登录状态，再检查模型名称，然后重新运行。
- **使用自己的终结点时出错**，例如错误信息中提到 `set-your-endpoint.invalid`，或者出现 `LLM judge failed: 401`：请参阅[使用你自己的终结点](#使用你自己的终结点)和[故障排除](../../reference/troubleshooting/)。

## 使用你自己的终结点

评审也可以不用 Copilot，而是在你自己的模型终结点上运行：如果你不想让评审占用你的 Copilot 计划，或者你的团队已经有用于评估的模型部署，这样做会很有用。你需要一个支持 Azure OpenAI v1 API 的终结点，例如在 Azure OpenAI 或 Microsoft Foundry 中部署的 GPT-5 系列模型（该系列支持 Responses API）。[模型访问与费用](../../start/model-access/#你自己的模型终结点可选)介绍了可选的方案。

<Steps>

1. 把终结点的基础 URL、密钥和部署名称分别填入 `LLM_BASE_URL`、`LLM_API_KEY` 和 `LLM_MODEL`：写在你的 `.env` 文件中，或者设为 Codespaces 机密。用一个小请求测试它们：

   ```bash
   ./scripts/check-setup.sh --ping
   ```

   最后几行应显示 `✔ HTTP 200 from <your deployment>` 以及模型的回复。

2. 在两个评估文件中，于 `defaults` 下、`judge_timeout` 的下方添加一个 `judge_provider` 块。它告诉 Vally 把评审的请求发到哪里：

   ```yaml
     judge_provider:                           # bring your own key: where the judge's requests go
       type: azure                             # Azure OpenAI-style API with an api-key header
       baseUrl: ${JUDGE_BASE_URL=https://set-your-endpoint.invalid/openai/v1/}   # replaced by --param
       wireApi: responses                      # use the Responses API
       apiKeyEnv: LLM_API_KEY                  # the NAME of the variable that holds the key, never the key
   ```

   配置了 `judge_provider` 之后，`judge_model` 指的是你的终结点上的部署名称。

3. 带上两个参数运行，它们分别填入终结点和部署名称：

   ```bash
   vally eval -e evals/judge-controls.eval.yaml \
     --param JUDGE_BASE_URL="$LLM_BASE_URL" \
     --param JUDGE_MODEL="$LLM_MODEL"
   ```

</Steps>

- **密钥永远不会写进文件。** `apiKeyEnv` 指定的是环境变量的名称，Vally 在运行时从这个变量中读取密钥。评估文件会被提交和共享，而密钥绝不能这样。
- **假的默认值是有意为之。** 有了 `https://set-your-endpoint.invalid/openai/v1/`，`vally lint` 在任何地方都能检查这个文件，即使是在没有终结点的 CI 中。如果你忘了加 `--param`，评审会失败，并报出一个提到 `set-your-endpoint.invalid` 的错误，而不会悄悄调用其他终结点。
- **`scripts/catch-up.sh 5`** 会把两个文件恢复为使用 Copilot 的版本；之后请重新添加这个块。

我们用一个兼容 Azure OpenAI 的终结点和 `gpt-5.6-luna` 测试过这种方式：判定结果与使用 Copilot 评审时相同。
