## 选好第一个目标

挑选一个**经常用到**、**规模小**，而且**以前失败过**的对象，最好你还记得它当时是怎么失败的。好的第一个任务要有明确的正确答案，两位同事都会认同。避免那些“好不好”主要取决于个人品味的任务；等你有了经过校准的 LLM 评审，再加入这类任务。

## 再走一遍循环

<Steps>

1. **定义“好”**（练习 1）。在运行任何东西之前，写下四到六条标准，其中至少包含一条“绝不能”。标出哪些标准可以用代码检查。

2. **起草评估（eval）**。从模板开始，或者让 Copilot 来起草（练习 6），然后对照你的标准审查草稿：

   ```bash
   cp lab-files/lab-9/my-first.eval.yaml evals/
   ```

   替换每一个 `TODO`：技能的文件夹、它需要的文件、一个贴近实际的提示词，以及对应你的标准的检查项。

3. **检查你的检查项**（练习 2）。复制一份并设置 `executor: mock`，把一个已知正确的答案和一个已知错误的答案放进提示词，确认判定结果符合预期。在这份副本中只保留针对答案的检查项：使用模拟执行器（mock）的运行不会调用工具，也不会修改文件，所以针对运行记录（transcript）的检查项（例如 `skill-invocation`）在那里无法通过。

4. **运行试验**（练习 3）：先运行 `vally lint -e evals/my-first.eval.yaml --strict`，再运行 `vally eval -e evals/my-first.eval.yaml`。要阅读运行记录，而不只是看通过率。

5. **修复并证明**（练习 4）。只改动一处，然后用实验进行比较。

6. **评判代码无法评判的内容**（练习 5）。只针对需要判断的标准添加评分标准（rubric）和 LLM 评审，并且先校准评审。

7. **为它把关**（练习 7）。给评估加上 `lane: ci` 标签，让每个拉取请求都运行它。

</Steps>

## 来自工作坊的建议

- **不要在提示词中点明技能或答案**。写出真实用户会输入的请求。
- **为你见过的每个 bug 添加一个否定检查**。bug 往往表现为多出了某些东西。
- **在关键之处检查运行记录和工作区**，而不只是检查答案。
- **保持运行相互隔离**。使用令牌登录，而不是使用 `EVALUATE_USE_HOST_COPILOT_HOME=1`，这样你自己的技能和设置就不会混入运行中。
- **先从 3 次试验开始**；在做出任何重要决定之前，要运行更多次试验。
- **把每一次真实的失败都变成新的任务或对照用例**。你的评估每抓到一个 bug，就会变得更好一些。
